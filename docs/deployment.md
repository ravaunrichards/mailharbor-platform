# Deployment and operations

## Render Blueprint

The root \`render.yaml\` declares:

- \`mailharbor-api\`: public Node.js web service, same-origin frontend/API, health check at \`/health/ready\`.
- \`mailharbor-delivery-worker\`: private background worker that polls PostgreSQL and sends queued mail.
- \`mailharbor-realtime\`: public WebSocket service that pushes owner-scoped mailbox change events from PostgreSQL notifications.
- \`mailharbor-db\`: PostgreSQL database referenced by both services.

The Blueprint currently selects starter web/worker resources and a basic PostgreSQL plan in the Ohio region. These are paid resource plans. Review the current price and region in Render before syncing the Blueprint. Do not sync it until you are ready to create those resources.

During Blueprint setup, enter:
- \`APP_BASE_URL\`: the final HTTPS URL of the MailHarbor web/API service.
- \`SMTP_HOST\`, \`SMTP_USER\`, \`SMTP_PASSWORD\`, and \`MAIL_FROM\`: values issued by your real mail provider.
- Leave generated \`JWT_SECRET\` and \`INBOUND_WEBHOOK_SECRET\` values generated by Render.

The API and worker must receive the same database and SMTP configuration. The Blueprint wires the realtime browser URL to the realtime service's public hostname. Set \`REALTIME_ALLOWED_ORIGINS\` on the realtime service to the exact HTTPS origin of the deployed API (for example, \`https://mailharbor-api.onrender.com\`); this avoids a circular service-reference dependency. Only the API needs \`APP_BASE_URL\` and inbound webhook secret.

## Release sequence

The Blueprint creates an additional paid starter web service for realtime delivery. Review its plan before syncing. The API issues one-use tickets; do not configure a second JWT secret on the realtime service.

1. Create the PostgreSQL and service resources from the reviewed Blueprint.
2. Wait for PostgreSQL to become available.
3. Set SMTP and sender-domain credentials on both services.
4. Set the API \`APP_BASE_URL\` to its deployed HTTPS origin.
5. Wait for the API to apply the versioned migrations and pass \`/health/ready\`.
6. Confirm the worker logs show a verified SMTP connection.
7. Register a test mailbox, receive its verification email, and verify the address.
8. Send a test email to an independently controlled recipient and confirm provider acceptance and final delivery.
9. Configure inbound routing and verify the signed webhook with an actual received email.
10. Configure backups, alerts, provider bounce/complaint handling, and abuse controls before public launch.

## Monitoring

- API liveness: \`/health/live\`.
- API readiness: \`/health/ready\`; checks PostgreSQL and reports whether mail capabilities are configured.
- Worker logs: SMTP connection, successful provider acceptance, retry scheduling, and final failures.
- Database: monitor storage, connection counts, backups, and migration history.

A message marked \`sent\` means the SMTP provider accepted it. It is not a guarantee of recipient inbox placement. Investigate provider bounce and complaint events using the provider dashboard until a provider-specific event adapter is implemented.
